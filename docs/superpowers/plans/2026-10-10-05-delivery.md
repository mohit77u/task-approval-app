````markdown
## Features

- Admin: create, edit, delete (soft delete) and assign tasks (title, description, priority, due date); sees all tasks.
- Employee: sees only assigned tasks, comments on them, moves them Pending → In Progress → Pending Approval.

- Dashboard: counts per status, scoped to what the signed-in user may see.
- Filters: status, priority, and (Admin) employee; debounced search; pagination; filters live in the URL.

### Workflow

| From | To | Who |
|---|---|---|
| Pending | In Progress | Assigned employee |
| In Progress | Pending Approval | Assigned employee |
| Pending Approval | Completed | Admin |
| Pending Approval | In Progress (reject, reason required) | Admin |

The rules live in one pure function (`backend/src/modules/tasks/task-state-machine.ts`). The API returns `allowedTransitions` on every task for the current viewer, so the UI renders from it and never duplicates the rules.

## Architecture

```
Browser ──HTTPS──▶ Vercel (Next.js, App Router)
                      │  rewrites  /api/*  (server-side proxy, same origin for the browser)
                      ▼
                  Render (NestJS, REST)  ──TLS──▶  Aiven MySQL
```

- **Why a proxy:** `*.vercel.app` and `*.onrender.com` are different *sites*, so calling the API directly would make the auth cookies third-party and Safari / incognito would drop them. With the proxy the browser only ever talks to one origin and cookies stay first-party. CORS is still locked to an exact allow-list.
- **Auth:** 30-minute JWT access token plus a 1-year opaque refresh token. Both live in `httpOnly` cookies. Refresh tokens are stored only as SHA-256 hashes, rotated on every use, and reuse of a rotated token revokes the whole token family. The frontend refreshes transparently (one refresh at a time) and retries.
- **Authorization:** enforced in the backend: a global JWT guard, a role guard, and per-query scoping (`TasksService.createScopedQuery`) so employees can only ever read their own tasks. Other people's task ids answer `404`.
- **Data:** MySQL via TypeORM entities with migrations (`synchronize: false`). Tables: `roles`, `users`, `tasks`, `task_comments`, `task_status_history`, `refresh_tokens`.
- **Errors:** every failure uses one shape `{ statusCode, code, message, details?, requestId, timestamp, path }`; the frontend normalises everything into one `ApiError` and shows it as a toast.
- **Frontend state:** Redux Toolkit + RTK Query. One `baseQuery` handles re-auth, retry of GETs against a sleeping server, and error normalisation; one middleware turns mutation successes and API errors into toasts.

```

frontend/  Next.js app (App Router, RTK Query, shadcn/ui)
docs/      design spec, implementation plans, AI-usage note

## Security notes

bcrypt password hashing; parameterized queries only (TypeORM); input validation with a whitelist (unknown fields are rejected); `httpOnly` + `Secure` + `SameSite` cookies; refresh-token rotation with reuse detection; helmet; strict CORS allow-list plus an `Origin` check on state-changing requests; rate limiting (login limited per email+IP); no secrets in the repository.

## Known limitations

- **One session per browser profile:** cookies are shared across tabs, so two roles at once need an incognito window or another browser.
- **Free-tier hosting:** the API sleeps when idle (first request can take about a minute); an uptime monitor pings `/api/health` to reduce this. The free database has no SLA.
- **Long-lived refresh token:** the requested 1-year lifetime is a deliberate convenience trade-off, mitigated by rotation, reuse detection, hashing at rest and server-side revocation. A production system would likely use a shorter lifetime with an absolute session cap.
- **Roles are data, permissions are code:** adding a row to `roles` makes it selectable when creating a user, but what that role may do is defined in guards and the state machine. There is no dynamic permission system.
- **Out of scope:** user deactivation and password reset, email notifications, file attachments, real-time updates, i18n.
- A task's comment thread is capped at 500 comments per response.
````

````markdown
## How API calls work

The browser calls relative `/api/...` URLs. `next.config.ts` rewrites them to `BACKEND_URL`, so cookies are first-party.

- `services/api/baseQuery.ts`: one entry point for all requests. On an expired session it refreshes once (shared by concurrent requests) and retries; it retries GETs while a sleeping backend wakes up; it normalises every failure to an `ApiError`.
- `store/middleware/apiNotificationMiddleware.ts`: the only place API outcomes become toasts. Every mutation success and every API error is announced; components contain no toast code.
- `lib/apiMessages.ts` (success wording) and `lib/apiNotification.ts` (error level mapping) are the two tables to edit to change messages.
- Task status changes go through the status dropdown with a confirmation dialog; selectable options come from the backend's `allowedTransitions`.

## Structure

```
src/app/            routes: (auth)/login, (app)/dashboard | tasks | tasks/[id] | users
src/components/     ui (shadcn), layout, common, tasks, dashboard, users, auth
src/hooks/          useAuth, useApiAction, useConfirm, useDebouncedValue, useTaskFilters
src/services/api/   RTK Query endpoint groups
src/store/          store factory, slices, notification middleware
src/lib/            pure helpers (errors, dates, filters, messages) with unit tests
```
````
